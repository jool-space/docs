Building kernels

What kernel packages build kernels with: the kernel cache, generated and concurrently.

Tempest.Compiler.content_key — Function
content_key(parts...; checked = false) -> String

A hash of parts that is the same in every session for the same content: of their canonical_text. With checked, Tempest's own code is named without its identity, for a kernel stored with what it depends on of that code (dependencies), from Julia 1.12, whose inference keeps the edges to find it.

source
Tempest.Compiler.cached_kernel — Function
cached_kernel(compile, key) -> (entry, binary)

The kernel under key: from the object cache, or compiled by compile(), which returns (entry, binary) and stores it, when the cache has none. This happens once per key in a session, so that callers in flight together wait for the first, and a failure fails every caller. The kernel is loaded or compiled on a thread from the moment it is asked for, as neither makes a device object: the tasks that build a stage's options side by side (concurrently) take turns on one thread, and a compilation they ran there would begin only once the last of them had asked for its kernel, as the GPT step's first stage of 147 kernels asked for its last 2.8 s in.

source
Tempest.Compiler.store_kernel — Function
store_kernel(key, entry, binary; dependencies) -> (entry, binary)

Count a compiled kernel and keep it under key, with what it depends on of Tempest's code (see dependencies), which a key that leaves that code out needs. A failure to write only loses the entry.

source
Tempest.Compiler.store_failure — Function

Count a kernel that failed to compile and keep the compiler's message under key.

source
Tempest.Compiler.cached_failure — Function
cached_failure(key)

Fail again, with the compiler's message, if the kernel under key failed to compile before (store_failure); otherwise do nothing. A kernel keyed without Tempest's code checks its failures under the whole key.

Tempest.Compiler.dependencies — Function
dependencies(code, lookup) -> Vector{UInt8}

What a kernel compiled from the code instance code depends on of Tempest's own code, written out: each method of Tempest or its extensions its inference reached, with its lowered code; each such global it read, with its value; and the fields of each such type its methods were specialized on. They are found through the edges inference keeps, lookup(mi) giving the code instance of a method instance an edge names, as the compiler that inferred them caches it.

source
Tempest.Compiler.uncached_kernel — Function
uncached_kernel(entry, binary) -> (entry, binary)

Count a kernel compiled in this session that the cache cannot keep, one that refers to values of the session, and return it as cached_kernel expects.

Tempest.Compiler.generated — Function
generated(source::Expr, into = Generated) -> function

Define the function source, an anonymous function expression, in module into, keeping its source: in a content_key a generated function is its source, since its name differs between sessions. A package's precompile workload defines its kernels in a module of its own, since Generated is closed to it then.

source
Tempest.Compiler.concurrently — Function
concurrently(f, xs, target) -> results

f of each of xs, in tasks that take turns on the calling thread, each in the calling task's state on target. Groups and kernels are built this way: while one task waits for its kernel, compiling on a thread of its own (see cached_kernel), the others ask for theirs. Device objects are made on the calling thread, so at exit they are finalized after what the caller made from them later (a module unloaded before a captured graph that launches it crashes the driver). It returns once every task has ended (see ended_all).

Tempest.Compiler.same_storage — Function
same_storage(a, b)

Whether buffers a and b are one storage: the same elements at the same address, whichever array holds them. Values over one argument's storage each hold a vector of the caller's array, made apiece (see share!), so that two of them are one storage and never one object.

Tempest.Compiler.SessionTable — Type
SessionTable{K, V}()

A table of answers kept for the session, read and filled under its own lock: how the compiler and the packages that implement its targets keep what they find once a session. A table is one only if its key holds everything its answer was derived from that can differ between two questions in one session, so that emptying it (forget_session!) costs time and never a wrong plan; any other table of theirs is named, with why, in NOT_SESSION_TABLES. A key holds, of what can differ:

  • code, named as the stores' content keys name it (definitions): a package's by the package, which is the same all session (its identity is found once, package_identity), so by the function itself; any other, a function of Main or a closure over one, by its definition, which a redefinition changes and the function object keeps;
  • the device, by what the answer read of it: its architecture, its context;
  • the environment's settings the answer read, and what the preparation that asked was asked, as whether it compiles (Implement.compiling);
  • content, as a kernel's, by its content key.

Answers are their session's: a table filled in another process, as a package's precompile workload fills its tables in the package's image, compiled on another machine perhaps and compiling nothing, holds none in the session that loads it (SESSION).

Code is named by content rather than by the world it was found in, Julia's rule for its own compiled code: every build defines its kernels' functions (generated), so a world in the key would never be met again by a later preparation, and Julia's validity for a range of worlds rests on the edges only its own compiler keeps. Content is how the stores already name code; a session table keys as a store does, with the session's one difference that a package's code is fixed.

An answer missing is found outside the lock and kept with get!(table, key, answer), the first kept winning where two tasks found one at once: the same answer found twice. get!(f, table, key) does both, finding it by f(); a caller whose f would be a closure over a value of its own type each time, a kernel's function say, looks up with get and keeps with get!, so as not to compile a closure for each. Where finding an answer twice is more than waste, as a kernel's compilation is, making it once is the table's own business: its value is what makes it, created under the lock (cached_kernel).

Tempest.Compiler.definitions — Function
definitions(code) -> Vector{String}

What a session table's key holds of code, functions, folds and types an answer was derived from, beside the objects themselves (see SessionTable): the content key of each no package identifies (see content_key), which writes it by its definition, as a store's key does, so that a function redefined in the session, the same object, is another key. A package's code is named by the object alone, since its package is the same all session. Sorted, so that code named in any order is named alike.
