Adding a target

A target is where a program runs. A package that adds one defines the names below for its type, as CUDAExt does for CUDATarget; the CPU's definitions are Tempest's own.

Tempest.Compiler.Target — Type

Where a program runs: CPUTarget, CUDATarget, or a type a package adds, defining the protocol of this file for it.

source
Tempest.Compiler.target_for — Function
target_for(x) -> target or nothing

The target an argument selects: CPUTarget() for an Array, a package's target for its arrays, on the device that holds them, nothing for anything else. A program is prepared on the first target among its inputs.

source
Tempest.Compiler.device_of — Function
device_of(x) -> Int or nothing

The device whose memory holds x, an array or a target's storage, by the number its package gives it; nothing for the host's memory, the CPU's. A target reads arrays on the host, copying them where they cannot be its storage, and the CPU reads a device's arrays so. A program whose arrays are on several devices is planned with a device for each value and a copy where a value is read on another (see plans_across_devices); on a target that does not plan so, its arrays and the target are on one device at most, beside the host, and a call that brings arrays of another device than its target's throws (see point!).

source
Tempest.Compiler.default_device — Function
default_device(target) -> Int or nothing

Where a target that names no device is at home when no argument is on one: the host's memory for the CPU, the calling task's device for CUDA.

source
Tempest.Compiler.at_home — Function
at_home(target, device) -> target

target at home on device: what a preparation builds and times with, once its arguments have said where home is.

source
Tempest.Compiler.on_device — Function
on_device(f, target, device = home_device(target))

f() with the calling task on device of target's kind, its state on the device it was on (for CUDA, its context and stream) as it was when f returns or throws: what touches a device, building, binding and running a program, runs on its own, whatever device the caller is on. An executable's steps are put on theirs by walk alone. A target of no devices, as the CPU, runs f() as it is.

Tempest.Compiler.download! — Function
download!(target, x, buffer) -> x

Copy buffer, storage on target, into the array x, which is not: how what a program wrote into an argument gets back into a caller's array that could not be its storage (see point!).

Tempest.Compiler.bindable — Function

Whether array x can be storage on target, bound by reference.

Tempest.Compiler.pointable — Function
pointable(target, x, at) -> Bool

Whether launches built on storage target allocated can read array x, whose first element is at address at, where it is instead (see repoint!): x is storage the target could have allocated, as aligned as its kernels assume of what it allocates.

source
Tempest.Compiler.task_state — Function
task_state(target) -> function

A function that, called first in a new task, gives the task the state on target of the task that asked for it (for CUDA, its context and stream), and none where that task has none: a preparation that builds nothing asks implementations side by side what they offer (see side_by_side), and touches no device, as while a package precompiles without one.

source
Tempest.Compiler.floor_launch — Function
floor_launch(target, kernel::ScalarKernel, args) -> launch

A launch of a floor kernel on target: launch() computes every item of kernel over args, the buffers of its slots and workspaces as a tuple. The CPU runs the items in order, in a function generated from the kernel's body; a device runs them at once, one thread per item, so a scatter's items add with accumulate!. A kernel with a split runs each lane of each part of each item, in the names its body reads: lin the item, part of parts, and lane of lanes in the part; the CPU runs a part as one lane.

source
Tempest.Compiler.ScalarKernel — Type

A kernel of the floor: body computes item lin, zero-based, of items, over the buffers of the values slots, dense and one-dimensional, and then those of its workspaces, which the function generated from the body receives as a tuple in that order (see floor_launch). A kernel with a split computes one lane of a part of each item.

source
Tempest.Compiler.accumulate! — Function
accumulate!(fold, buffer, i, x)

Combine element x into state i of a fold by key, in buffer: in place on the CPU, where a floor kernel's items run in order, and atomically on a device (see CUDAExt), where they run at once and the elements a position takes combine in no fixed order.

source
Tempest.Compiler.floor_split — Function
floor_split(target, items, positions, adjacent) -> Split or nothing

How the floor folds positions positions for each of items items on target, neighbouring items neighbours in memory when adjacent: nothing for one lane per item, which folds them in order, as on the CPU; or a Split, which deals them among lanes. A target that splits runs a part's lanes together and merges their states with merge_lanes.

source
Tempest.Compiler.Split — Type
Split(parts, lanes, side = 1)

How the floor deals the positions each item folds among lanes, where items alone would leave a device idle: parts parts of lanes lanes each, as the target asks for it (see floor_split). Each lane folds every parts * lanesth position from its own, the lanes of a part merge their states (merge_lanes), and a part keeps its state in a workspace, which the next launch merges with the item's other parts'. So a split group is a launch per phase of its folds, and one after them that stores them and sweeps what reads them, its positions dealt among the lanes as the folds' were. On CUDA a part is a block and its lanes threads, the same part of side neighbouring items in one block, side by side; on the CPU a part has one lane.

source
Tempest.Compiler.merge_lanes — Function
merge_lanes(fold, state, workspace) -> state

The merge of state over the lanes of a part of a split item (see Split), which each lane gets. The fold's workspace names the target, as the buffer of accumulate! does: on the CPU, where a part has one lane, the merge is state itself; on a device the lanes merge their states (see CUDAExt).

source
Tempest.Compiler.Step — Type
Step(run, device, from = device)

A step of an execution: run(), a kernel's launch or a copy, and the device it runs on (see device_of); and the device it reads from, another only for a crossing, a copy from from to device (see crossing). The two name the stream it runs on: a device's own (see stream), or the lane of the ordered pair of devices a crossing copies between (see lane).

source
Tempest.Compiler.crosses — Function

Whether a group of the kind reads on another device than the one it writes on: a crossing's, which copies a value from the device it is stored on. A group of any other kind reads and writes on one.

source
crosses(step) -> Bool

Whether step copies between two devices, a crossing's (see crossing), on the lane of the two rather than on a device's own stream: a target with graphs says how a run of crossings is recorded (see capture).

source
Tempest.Compiler.taken — Function

The kernel formed there from seed, where forming it here, through context cx, would read nothing that differs.

source
taken(target, x)

Take x, an array a call shares with its caller, a result or an argument bound by reference, for the launches the call is about to make, with the task on the array's device: the launches read and write it by its address, unseen by the package whose array it is. What other streams still have to run on x is waited for, and whatever reads it after the call, on any stream or task, waits for the launches. A target whose arrays' package orders an array's uses by the stream each was submitted on takes the array's address here, which that package counts as the calling task's use of it from then on, until another stream's. The CPU's run in order, and it does nothing.

source
Tempest.Compiler.crossing — Function

Whether value v of graph is read across devices: a crossing's copy.

source
crossing(target, to, from, values, offset) -> run

A step's run that copies into buffer to, storage on another of target's devices, as many elements of buffer from, storage on one, as to holds, those after the first offset: how a value read on another device than its own gets there (see Crossed), all of it at offset 0, or a span of it, which is all its readers there read (see storage_span). values names the two buffers, to_value => from_value, for the run to be pointed elsewhere as a Copy is (see repoint!); the offset is the run's own, where in the source value's storage the span starts, kept as either buffer is replaced. It is built with the task on to's device, and runs where its lane puts the task (see on_stream); each buffer knows its own device. Its schedule orders it after what wrote its source and before what reads its copy (see Schedule). A target with graphs says, as it records a run of crossings (see capture), whether the crossing is recorded or runs as the run is replayed. On the CPU, whose devices are labels on the host's memory, it is a copy on the host.

source
Tempest.Compiler.stream — Function
stream(target, device) -> stream

What a device's own steps run on (see stream_of), its kernels and copies in order. Made once for each schedule, with the task on the device. By default the pair (device, device), whose steps run with the task on the device (see on_stream).

source
Tempest.Compiler.lane — Function
lane(target, from, to, out) -> stream

What the crossings from device from to device to run on (see stream_of), in order: the lane of the ordered pair, which leaves from by out, its link (see link). Made once for each schedule, with the task on to's device. By default the pair (from, to), whose steps run with the task on to (see on_stream).

source
Tempest.Compiler.link — Function
link(target, device) -> link

What the crossings leaving device go out by, every lane from it the same (see lane): it takes them one at a time, in the order they are launched, which is the order their sources are written (see walk and run_order), so that none waits behind one whose source is not. Made once for each schedule, for each device a crossing leaves, with the task on it. By default nothing: the CPU's crossings are copies on the host, which run as they are launched.

source
Tempest.Compiler.on_stream — Function
on_stream(f, target, stream)

f() with the calling task where the steps of stream run, as on_device puts it on a device. By default on the stream's last device: a device's own, or the reader's of a lane, where a crossing's run is built and expects to run (see crossing). A target whose lanes are streams of their own enters them here.

source
Tempest.Compiler.task_stream — Function
task_stream(target) -> stream

The stream the calling task's launches run on, on the device the task is on (see on_device): what an executable keeps of its last use on each device, and compares with the next (see taken!). On a target whose steps have run as they return, the CPU's, nothing.

source
Tempest.Compiler.event — Function
event(target, stream) -> event

What a step on stream records once it has run, for steps on other streams to wait for (see record! and wait!), made with the task where the stream's steps run. A target whose steps run in the order they are launched, the CPU's, has none: nothing.

source
Tempest.Compiler.record! — Function
record!(target, stream, event)

Record event on stream, after what was launched on it so far, with the task where the stream's steps run (see on_stream): after a step that a step on another stream waits for, and as a call begins and ends (see walk). Recorded into a graph (see capture), each launch of the graph records it again.

source
Tempest.Compiler.wait! — Function
wait!(target, stream, event)

Make what is launched on stream from now on wait for what was launched before the last record! of event, with the task where the stream's steps run (see on_stream): before a step that waits for a step on another stream, and as a call begins and ends (see walk). Recorded into a graph, the wait is for the last record launched before the graph.

source
Tempest.Compiler.Scheduled — Type
Scheduled(step, stream, waits, signal)

A step as its schedule runs it (see Schedule): on stream (see stream), after waiting for waits, the events of steps on other streams, and recording signal once it has run, where a step on another stream waits for it, else nothing. What a target captures and replays (see capture).

source
Tempest.Compiler.capture — Function
capture(target, steps, keep) -> graph

steps, each a Scheduled step that launches work on target, all on one stream (a run of a Schedule), captured in order, their waits and records with them, as one graph for replay(target, graph) to launch again; retarget! changes the addresses one step's work reads. Tempest asks with the task where the stream's steps run (see on_stream), where the graph is made, launched and changed. The graph keeps keep, what it launches, alive until release(target, graph) or the collector destroys it. A target without graphs replays the steps themselves.

source
Tempest.Compiler.replay — Function

Launch graph, what capture recorded on target.

source
replay(d, r) -> Decided or nothing

Decisions r replayed on decider d's graph: the plan of the proposals taken, planned once, each group's text checked against the one kept, and each recurrence's step replayed from those kept with them. Nothing where a group differs or a step was not kept: the cover reaches them instead.

source
Tempest.Compiler.release — Function

Destroy graph, what capture recorded on target, once nothing replays it.

source
Tempest.Compiler.recapture — Function
recapture(target, graph, steps, keep) -> graph

graph, which capture recorded from steps, recorded again after their launches were pointed at other storage (see repoint!). A target with graphs may update the graph it has rather than make another.

source
Tempest.Compiler.retarget! — Function
retarget!(target, graph, steps, moves, repoint) -> Bool

Make what graph recorded of a launch, steps among the steps capture took, read where moves say its values moved, each a named tuple of the value, its old and new addresses and its bytes, (value, from, to, bytes). repoint() points the launch at the new storage (see repoint!), and is called once, by the target or after it: a target may record the launch alone before and after, to learn where its recording holds an address. False when the graph cannot be changed so, and must be recorded again (recapture). The steps themselves, a target's graph without graphs, read where their launches read: true.

source
Tempest.Compiler.device_name — Function
device_name(target[, device])

The name of the device target runs on, which names its tuning record and its rates file; or of another of its devices, as device_of numbers them, which a program placed over several runs on (see Placement). A target's devices are of one kind unless it says otherwise.

source
Tempest.Compiler.toolchain — Function
toolchain(target) -> Vector{Pair{String, String}}

What builds the kernels target runs, each part by name and version, which names its tuning record and its rates file with its device: what they hold are times of kernels built so, and a kernel another toolchain builds is another kernel to time. Nothing for a target that builds none, as the CPU.

source
Tempest.Compiler.measurable — Function

Whether claims on target can be timed at preparation; time_launch times one.

source
Tempest.Compiler.time_launch — Function
time_launch(target, launch) -> seconds::Float64

The seconds one call of launch() takes on the device among the launches of a captured graph, its data in memory rather than in the cache, as the cover times claims: a step reads its weights once, and finds them in memory. Only a measurable target defines it. Tempest calls it one timing at a time, once the device's work is done, so what it keeps between timings needs no lock.

source
Tempest.Compiler.time_crossing — Function
time_crossing(target, from, to, bytes) -> seconds::Float64

The seconds a crossing of bytes from device from to device to of target takes (see crossing), run alone on the lane of the two (see lane), from when the lane may start to when what reads the copy may: what a decider fits the link between them on (see link!). Only a measurable target that plans across devices defines it. Tempest calls it one timing at a time, once both devices' work is done.

source
Tempest.Compiler.quiesce — Function
quiesce(target, stream)

Wait until stream, a task's as task_stream gave it, has run everything that task launched on it, with the calling task on the stream's device: a task that uses an executable another stream used last waits so (see taken!). The CPU's steps have run as they return, and it does nothing.

source
quiesce(target)

Wait until the device has run everything launched on it, by any task. Every timing waits so before it times a claim (see timed).

source
Tempest.Compiler.device_rates — Function
device_rates(target) -> rates

The device's rates as it reports them (see Rates): a named tuple of launch, the seconds between launches in a captured graph; cached and bandwidth, bytes per second for a launch that moves what the cache holds and for one that moves more, each from memory; cache, its bytes; and blocks, the blocks that fill the device. They are not measured: off by twice or half, they change no plan of the corpus's, and the rates that do, each package's products and each scalar function's seconds, are fitted on first need. Only a measurable target defines it.
