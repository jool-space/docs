API

Tempest — Module

Tempest compiles traced Julia array programs into planned, fused kernels.

A program is Julia array code, and what it computes reaches the compiler as three things: maps, folds (a scan is a fold that keeps the axis it runs along, a scatter one that combines each element at a position it computes), and reads at index formulas. Products, reshapes, permutations, gathers and scatters are spellings of them, and so is every function a program calls. Tempest names only what Base cannot spell:

  • the way in: compile, explain, gradient and withgradient, the targets, and the implementations of kernel packages Tempest has extensions for;
  • the derivative of a scalar function, which its code does not carry: scalar_partials, and a value no gradient flows through: stopgrad;
  • the laws of a fold's combine: GenericFold.

A fold is Base's mapreduce, its state a tuple if need be, and a scan Base's accumulate; a fold's derivative comes from its combine's, through scans. A function given to mapreduce is taken to associate and commute, as a reduction groups and interleaves its elements; one given to accumulate is combined in sequence, as Base combines it, from an init that need be no identity. A GenericFold, given to reduce or accumulate where the function goes, claims that it associates and commutes, and so a scan by it may group its elements, as a sum's may.

logsumexp is a fold, a spelling. The log-sum-exp written out with maximum differentiates as it does, and plans as it does where the target permits the rewrites of sums (see Compiler.rewrite); it is named still because where a target keeps the rounding as written, the spelling is two passes, the maximum and then the sum, and logsumexp one.

Any other function, a product by labelled axes or a batched product say, is a spelling and lives in its own package, as Einops's and NNlib's do; an extension gives it a method on traced arrays where its body does not trace.

Tempest.Compiler is how a program becomes kernels; its public names are what packages beside a program need: the step beneath compile, what an extension writes traced methods with, and what kernel packages and targets read and define. Compiler.IR is the vocabulary its levels share and implementations read, and Compiler.Implement the interface kernel packages implement.

Compiling a function

Tempest.Compiler.compile — Function
compile(f, args...; target, measure = :close, capture = true) -> Compiled

f traced on args and prepared, to be called like f: compile(f, x)(y) computes f(y) for any y alike x in structure, shapes and element types. It returns what f returns, in arrays of its own, with numbers as numbers, and what f writes into an argument's arrays it leaves there, as f would.

measure says which claims are timed when preparing, as for prepare: :none none, :close the options whose estimates are close, :all every option; true and false mean :close and :none. The default is TEMPEST_MEASURE's where the environment sets it.

Which leaves of the arguments are inputs follows trace: arrays, also inside tuples, named tuples, structs, mutable ones too, and vectors of other things than numbers, whose lengths a call must match. An array the function reads inside any other leaf, a dictionary's say, would be a constant, and is refused, naming the argument. Numbers are constants; a number that varies between calls is an array, [x] say. f is an argument like the others, the call f(args...) traced: the arrays of a callable struct's fields and those a closure captures are inputs too, read at each call, so a closure over a model sees its weights as they are when called.

A global that f reads is no part of f, and tracing reads it once. One holding arrays is refused, since the program would keep them as they were when traced: pass it as an argument. In f's own code a global is seen by its name; in a function f calls, by its arrays: an array tracing meets that lives in a global, of any module, is refused alike, as is a global a function assigned while traced. Any other global f's own code reads is a constant, and one not declared const is checked at each call. A number a function f calls reads, or a copy it makes of a global's array before using it with an input, is kept as it was when traced.

An argument's array is the program's storage for it, read and written where the caller has it, not copied: a call on the arrays of the call before costs nothing for them, and one on others changes the addresses the captured graph's kernels read and write, in place (see Tempest.Compiler.point!), so a training step whose weights are new arrays at every call copies none of them. The program is built on the arrays compile is given and holds no storage of its own for them, so a model's weights are in memory once; it holds the arrays of its last call, or until the first those it was compiled on, until a call brings others. What f writes into an argument the kernels write into the caller's array: where the kernel that writes it reads the array only at the addresses it writes, and the kernels that read it otherwise can run first, directly, as an append to a cache writes only its new positions; else into storage of the program's own and then copied into the array once, after the last kernel (explain says which). Everything else the program stores lives in buffers it owns and reuses at every call. An array not of the target's array type, an Array for a function compiled for the GPU say, is copied into a buffer the program makes the first time it needs one and keeps, and, if written, back after the call.

A call whose arguments, f's own leaves or the globals f reads differ in anything but the values of inputs throws, naming the difference. So does a call whose arrays share memory with one f writes: the program reads each array apart, where f run on them would read what it wrote.

julia> c = compile(x -> sum(abs2, x), [0.0, 0.0, 0.0, 0.0]);

julia> c([1.0, 2.0, 3.0, 4.0])
30.0

A function that writes its arguments is compiled as it is written, and its state stays where the caller keeps it:

julia> f!(s, x) = (s .= 0.5 .* s .+ x; sum(s));

julia> s = [1.0, 2.0]; c = compile(f!, s, [0.0, 0.0]);

julia> c(s, [1.0, 1.0]), s
(3.5, [1.5, 2.0])

With capture, the program's launches are recorded once as one graph that each call replays, as capture! and replay! do. Results are the same either way.

The level beneath is in Tempest.Compiler: prepare, bind!, and execute! or replay!, with point! binding a call's arrays as compile does. c.executable is the prepared program, and explain(c) shows it.

Tempest.Compiler.gradient — Function
Tempest.gradient(f, args...) -> gradients

The gradient of f(args...), a number, with respect to each argument, a tuple with one per argument, in that argument's structure: an array for each floating-point array, and nothing for anything else. Numbers are constants, among a gradient's arguments as among a program's, so a number to differentiate by is an array, [x] say. A struct's gradient is a named tuple of its fields', and a vector's a vector of its elements'. It is Zygote's gradient, and withgradient returns the value too.

In traced code it differentiates f where it is called, so a training step is a function like any other, traced and prepared as one program (see withgradient). What f closes over is a constant to the gradient.

source
Tempest.Compiler.withgradient — Function
Tempest.withgradient(f, args...) -> (val = value, grad = gradients)

The value of f(args...), a number, and its gradient with respect to each argument, as gradient returns it, as Zygote's withgradient does. On Julia arrays this is interpret(differentiate(trace(f, args...)), args...).

In traced code it differentiates f where it is called, so a training step is a function like any other, traced and prepared as one program:

function step(params, state, batch)
    loss, (grads,) = Tempest.withgradient(p -> loss_of(p, batch), params)
    new_params, new_state = adam(params, state, grads)
    (loss, new_params, new_state)
end

What f closes over is a constant to the gradient.

Tempest.Compiler.explain — Function
explain([io], c::Compiled)

Print what Tempest decided for a program. For each kernel: what it computes, what it reads, and which values it stores or leaves to be recomputed where they are read. For a prepared program, also the precision of its products, the close calls measured between implementations, how values share storage, which implementation runs each kernel, at what estimated or measured time, and the claims on it that failed to build.

It describes what Tempest decided today; what it prints may change.

Tempest.Compiler.CUDATarget — Type
CUDATarget(implementations...; precision = :full, online = true, rounded_backward = true, deterministic = false)

Run on an NVIDIA GPU; needs CUDACore loaded. The target uses the floor and the implementations given, as in CUDATarget(cuTileGenerator()), ties between their estimates going to the first; by default Tempest's own whose packages are loaded when it is made, cuBLAS's, cuDNN's and cuTile's (see cuBLASProducts, cuDNNAttention and cuTileGenerator). Another package's implementation takes part only when it is given, and with none at all, CUDATarget(precision, online, ()), the floor runs every kernel. precision is the numerics policy for products: :full keeps Float32 products in Float32, :tf32 allows TF32 tensor cores for them, and :tf32x3 splits each Float32 factor into two TF32 parts and sums three tensor-core products (close to Float32 accuracy). Half-precision products always accumulate in Float32, and a product of a half-precision value, read through its conversion to Float32, and a Float32 one is a half-precision product under any precision, the Float32 factor rounded to the half type: a BFloat16 attention's backward rounds its probabilities and their gradient so, as FlashAttention and cuDNN do, where the CPU multiplies in Float32 as the program does. The target trades that precision for speed as cu does, which makes arrays Float32. online permits the online softmax (see rewrite): a sum weighted by a softmax accumulates in one pass with the softmax's maximum, rescaled as it grows, which changes rounding. rounded_backward lets a backward read a forward's sum as the program rounds it to half precision where the sums of the derivative are exchanged (see exchanged_sums): the softmax backward's Σ dO·o reads the output o as a half-precision forward stores it, as FlashAttention and cuDNN read theirs, rather than in Float32, and the forward stores the rounded output only. With it false the backward reads the sum as the program computes it: in BFloat16 at 64 features, 8 heads, 1024 positions, the gradients' largest error is 6.2e-3 of their largest element rather than 6.8e-3 for a loss of the output's squares, where Σ dO·o nearly cancels the sums it is taken from, and 5.5e-3 either way when the output's cotangent comes from elsewhere. deterministic keeps a sum's rounding from depending on the order its blocks run in. Without it a sweep may compute a sum in the sweep's orientation and add it into its value atomically, as FlashAttention-2's backward adds the queries' gradient, which then differs from run to run in its last bits: attention's training step in Float32 at 1024 positions, 64 features, 8 heads, causal and TF32 takes 437 μs, and 702 deterministic. A sum by key, as an embedding's gradient is, accumulates atomically either way.

Writing programs

Programs are written with Base: broadcasts, folds (mapreduce with a tuple state among them), scans (accumulate, cumsum), products, indexing and ranges (a range broadcast against a traced array is the index itself, a formula rather than an array). Beyond Base, programs can call logsumexp, and claim with a GenericFold the laws of a combine, which Base cannot spell:

Tempest.Compiler.logsumexp — Function
Tempest.logsumexp(x; dims = :)

log.(sum(exp.(x); dims)), computed stably in one pass.

source
Tempest.Compiler.IR.GenericFold — Type
GenericFold(; init, combine, lift = tuple, observe = only, pullback = nothing)

A fold from functions, given to reduce or accumulate where the operator goes. lift maps an element to a state tuple, combine merges two, the earlier first, and observe maps the last state to the result; init is a state tuple or a function of the element type returning one. It claims what Base cannot spell: that combine associates and commutes, up to rounding, and init is its identity, so a reduction or a scan by it may group its elements in any order. A function given to accumulate is combined in sequence instead. pullback(x, y, g, axes), when given, is the derivative rule of a reduction by it.

julia> recurrence = Tempest.GenericFold(; init = E -> (1.0, 0.0), lift = identity,
           combine = ((a1, b1), (a2, b2)) -> (a2 * a1, a2 * b1 + b2), observe = last);

julia> accumulate(recurrence, [(0.5, 1.0), (0.5, 1.0), (0.5, 1.0)])
3-element Vector{Float64}:
 1.0
 1.5
 1.75

Tempest.Compiler.TracedArray — Type

An array a program is written with: a stand-in that records what is done to it as nodes of its tape. It is memory, as a Julia array is: an array the traced code allocates can be written, and views, reshapes and transposes share the memory of the array they are made from. A package that adds functions programs call defines them on it, in Tempest's primitives.

A number a program computes: a stand-in for a scalar result such as sum(x), and, inside a broadcast, for an element of an array, which the broadcast's function runs on, each primitive operation it performs recorded. A package whose scalar function does not trace, a ccall say, defines it on Traced in operations that do; scalar_partials rules receive it too.

Tempest.Compiler.contract — Function
contract(a, b, la, lb, lo)

The product of a and b summed over shared axes, as an einsum: la and lb label the axes of a and b, lo those of the result, and labels of both factors missing from the result are summed over. Every product is one: a * b of matrices is contract(a, b, (1, 2), (2, 3), (1, 3)), and so is each product of an Einops einsum.

Derivative rules

Tempest.Compiler.scalar_partials — Function
scalar_partials(f, y, xs...) -> tuple

The partial derivatives of y = f(xs...), a function of numbers, with respect to each argument: a handle or number per argument, or nothing where the argument has none. y is the result, which a derivative such as exp's reuses; the arguments are handles, or numbers where they are constants.

scalar_partials(::typeof(tanh), y, x) = (1 - y * y,)
scalar_partials(::typeof(/), y, a, b) = (1 / b, -y / b)

The caller multiplies each partial into the cotangent of y: a condition selects it where it holds, a reciprocal 1 / x divides it by x, and a partial no gradient needs is never computed. Define a method for a function Tempest records whole, one that branches on its argument, say, to make it differentiable, or for one whose code traces, to differentiate it by the statement where it is broadcast, where the code's derivative at a branch is not the function's.

source
Tempest.Compiler.stated_derivatives — Function
stated_derivatives(f, y, xs...) -> tuple or nothing

The partial derivatives of y = f(xs...) with respect to each argument, as f's package states them through ChainRulesCore's @scalar_rule, nothing for an argument with none; nothing for a function with no statement: Flux's xlogy, NNlib's activations and SpecialFunctions' erf state theirs. They are taken as the function's own where it has none of its own, for a function whose code traces, whose derivative at a branch may not be the function's, and for one recorded whole, whose code cannot be differentiated.

source
Tempest.Compiler.stopgrad — Function
Tempest.stopgrad(x) -> x

x itself, through which no gradient flows: a constant to every derivative taken of the code it is in, of any order. x is a number, an array, or a struct or tuple of them. Where x is used elsewhere, the gradient flows there. A straight-through rounding is

x .+ Tempest.stopgrad(round.(x) .- x)

rounded in value and the identity in derivative.

Tempest.Compiler

Tempest.Compiler — Module

How a program becomes kernels: the program, index and plan levels, the cover, code generation, the kernel cache, and prepared programs. Its public names are what packages outside it need: beneath compile, a program traced (trace) and prepared (prepare, bind!, execute!, capture!, replay! and outputs), for a step run in place; the language programs are written in, which Tempest makes its own, and what an extension writes traced methods with (TracedArray, Traced, contract); what implementations read of a plan beyond IR, and what they build kernels with (the kernel cache, generated and concurrently); and the protocol a package that adds a target defines (see Target).

Its submodules are IR, the vocabulary its levels share and implementations read, and Implement, the interface kernel packages implement. Their public names are what kernel packages read; the compiler also uses what they keep to themselves, such as the arithmetic that builds index expressions.

source
Tempest.Compiler.trace — Function
trace(f, args...) -> Program

Run f on stand-ins for args and record what it computes. Arrays among args, also inside tuples, named tuples, structs, mutable ones too, and vectors of other things than numbers, become the program's inputs. Numbers are constants, as configuration is: an integer can be a size, a layer's epsilon or a rule's rate is a number of the program, and a number that varies between executions is an array, [x] say. Each struct and vector is built anew around the stand-ins, so f never writes the caller's, and a vector's length is the program's. The results are arrays and numbers in the same kinds of structure, a vector among them built as map builds one, its element type the join of its elements'; any other leaf, nothing or a layer's function, is returned as it is.

f itself is code here: the arrays it holds, a closure's captures or a callable struct's fields, are constants of the program, copied when traced. To make them inputs, pass f among the arguments, as compile does: trace((f, x) -> f(x), f, x).

f may write into an input, as a layer updates its running statistics: what it wrote is the input's contents when the program ends, a result after those f returns, which replaces the input (see Program). Executed, the program leaves it in the caller's array, as f would.

julia> p = trace(x -> sum(abs2, x), [1.0, 2.0, 3.0])
Program with 3 nodes: Float64(3,) → Float64
  %1 = argument :: Float64(3,)
  %2 = map abs2 %1 :: Float64(3,)
  %3 = reduce sum over (1,) %2 :: Float64  [result]

Tempest.Compiler.prepare — Function
prepare(program, inputs...; target, measure = :close, replaces = (), by_reference = (), point = false, recompute = (), ride = (), build = true, verify) -> Executable

Plan program for the shapes and types of inputs and build its kernels on target, chosen from the inputs' array types by default. Close calls between claims are timed when measure allows and the target can, and kept in the tuning record. measure = :none times no claim but still uses the times in the record; :close, the default, times the options whose estimates are within the close-call factor of the best; :all times every option of every group and both sides of every comparison. true and false mean :close and :none. The environment's TEMPEST_MEASURE (none, close or all) sets the default, as the tests set it to none: on a device other jobs share, a close call timed is decided by chance.

What the cover decided, the proposals it took and the claim that runs each kernel, is kept beside the tuning record (see Tempest.Compiler.reach!), and a preparation of the same program, on the same target and device, with the record and the rates file holding what those decisions read, replays it: it plans the program once, and plans no trial, prices and measures nothing. Anything else a decision reads that differs, the program's extents, element types or captured constants, the target's numerics, Tempest's own code or a time recorded since, makes them the cover's to reach again. Decisions are replayed only where the cover would reach them again on the record as it is: a preparation that measured as it decided covers again on what it measured, until a cover measures nothing, three covers at most, and keeps the last one's; with the environment's TEMPEST_SETTLE=false it keeps the first's, which the next preparation reaches again. With TEMPEST_REPLAY=false a preparation neither replays decisions nor keeps its own: the cover reaches them every time. A fresh TEMPEST_CACHE holds no decisions, no record and no kernels.

A claim that fails to build is no option once it has: the program is planned again without it, each map of the group it claimed proposed to be stored apart, so that a scalar function a kernel package cannot lower runs on the floor and the rest of the group on the package. explain names the claims that failed.

replaces declares state, as pairs result => argument of positions among the program's results and its arguments, alike in structure, shapes and types: (2 => 1, 3 => 2) for a step (params, state, batch) -> (loss, params, state). After each execution the argument holds the result, as if bound again, so the next execution reads it where it is. An input the program writes is replaced so by what it writes; a result that is the input as it was before the write is copied apart before the kernels run. A result is written into the argument's storage when the kernel that writes it reads the argument only at the address it writes, and the kernels that read the argument otherwise can run first; else it is written apart and copied there after the last kernel. explain says which.

bind! copies inputs into storage the executable owns, except the arrays at the positions in by_reference, which must be of the target's array type: they are the executable's storage. The caller keeps them alive and may write them between executions, and a result that replaces one writes into it. point! makes the caller's arrays the storage at each binding instead, as compile does. The preparation binds inputs as bind! does, or as point! does with point = true, as compile prepares: the kernels are built on the caller's arrays where they can read them there, and the executable makes no storage of its own for those arguments until a binding copies into it, holding the arrays as point! does, until it is bound to others.

recompute pins folds to be recomputed where they are read rather than stored, by their numbers among the values of the program's index graph, as explain prints them: what the cover would otherwise decide by cost (see Tempest.Compiler.recomputable_folds). ride pins values computed from a recurrence's steps to be computed as the steps run, so numbered: a sum over the steps added at each, a value along them written at each, one of the last step written at it; what the cover would otherwise decide by cost (see Tempest.Compiler.riding_values). partition decides which of the forward's maps the backward recomputes rather than reads, by a minimum cut of what saving them costs (see Tempest.Compiler.partition); false saves every map the backward reads, as a trial's comparison.

build = false plans and decides but builds and allocates nothing: the executable can be explained, not run, on a machine without the target's device. No claim is timed, and claims are priced on nominal rates.

verify = true checks every plan the preparation forms, the cover's trials among them, and the storage of the one it runs, throwing where one breaks an invariant the kernels rely on (see Tempest.Compiler.verify). It is the default where the environment sets TEMPEST_VERIFY=true, as the tests do. Where it sets TEMPEST_CROSSCHECK=true, as the tests do too, decisions a preparation replays are checked against those its cover reaches, which it reaches as well, at a cover's cost.

A training loop, where the step returns the loss and the new parameters and optimizer state:

ex = prepare(trace(step, params, state, batch), params, state, batch; replaces = (2 => 1, 3 => 2))
capture!(ex)
loss = first(outputs(ex))       # where each step leaves the loss
for batch in batches
    bind!(ex, 3 => batch)       # only the batch is new
    replay!(ex)                 # parameters and state are updated where they are
    @show loss[]
end

A function that writes its arguments needs none of this: compile writes them where the caller has them, for any arrays a call brings.

Tempest.Compiler.bind! — Function
bind!(ex, inputs...)
bind!(ex, position => input, ...)

Copy inputs into the executable's input buffers: all of them, in the structure prepare took them, or those at the positions given, as a new batch while parameters stay where the last execution left them. An array bound by reference and bound again is not copied.

julia> ex = prepare(trace(x -> 2 .* x, [1.0, 2.0]), [1.0, 2.0]);

julia> bind!(ex, [3.0, 4.0]);

julia> outputs(execute!(ex))
2-element Vector{Float64}:
 6.0
 8.0

Tempest.Compiler.point! — Function
point!(ex, inputs...) -> ex

Bind inputs as compile's call does: an argument's storage is the caller's array, read and written where it is, when every launch can be pointed elsewhere (repoints) and the target can read and write the array where it is (pointable); the array is copied otherwise, as bind! copies, into a buffer of the executable's own made the first time one is, and each execute! or replay! after copies what the program wrote there back into it. An argument bound by reference keeps its array. An array the storage is already costs nothing. The steps that use the storage of one elsewhere, the kernels that read or write it and the copies of saved inputs and staged results, are pointed at it, the results over it are over it, and a captured graph is changed where it records their addresses (retarget!), or recorded again where the target cannot change it; recording again costs more than copying an array that moves every call, as a training step's weights do, so an argument whose graph was recorded again is the caller's array only once the caller brings the same array twice in a row. The executable holds the arrays it reads and writes until it is bound again.

source
Tempest.Compiler.execute! — Function
execute!(ex) -> ex

Run the program on the inputs bound last: copy the inputs it writes into the results that are them as they were before, launch every kernel in order, then copy staged results into the arguments they replace, and what it wrote into an argument into the caller's array point! bound it to, where that is not its storage. The results are in outputs(ex). Whether or not the program is captured, this launches kernel by kernel; replay! runs the capture.

source
Tempest.Compiler.capture! — Function
capture!(ex; repetitions = 1) -> ex

Record what execute! launches as one graph, for replay! to run, each replay repetitions executions of the program (for timing). Recording runs nothing. What varies between replays lives in device buffers: inputs bound by copy or by reference, scalars and seeds among them, are read where they are, so they need no new capture. Capturing again replaces the graph. On a target without graphs, a replay launches the kernels.

ex = capture!(prepare(p, CuArray(x)))
replay!(ex)                     # runs the graph
bind!(ex, CuArray(y))           # copied into the buffers the graph reads
replay!(ex)                     # the same graph, on the new values
source
Tempest.Compiler.replay! — Function

The nodes of program p recorded on inputs, handles of its arguments: a handle of each of its results.

source
replay!(ex) -> ex

Run what capture! recorded, on the inputs bound last: what execute! does, repetitions times over, as one launch of a graph on a target with graphs, then copy what it wrote into an argument into the caller's array point! bound it to, where that is not its storage. The results are in outputs(ex).

source
Tempest.Compiler.outputs — Function
outputs(ex) -> results

Where the executable leaves its results, in the program's output structure: arrays over its buffers, the same arrays every time, which each execute! or replay! fills again. Copy what you keep. A number is an array of no dimensions here, since it lives in a buffer too; compile returns numbers.

source
Tempest.Compiler.forget_session! — Function
forget_session!()

Empty every table of answers the session keeps (its compiled kernels by content, the functions loaded from them, which functions cuTile lowers, what identifies each package's code, among others), so that a preparation after finds each again, as one in a new process would. Julia's compiled code, the device's resources and the stores on disk stay: a new TEMPEST_CACHE and JULIA_OBJCACHE_PATH leave those behind too. Each table's answer is keyed by everything it reads, so that emptying them costs time and never gives another answer.

Tempest.Compiler.verify — Function
verify(plan) -> plan
verify(plan, storage; in_place = k -> true) -> plan

Check the invariants the kernels of plan rely on, and throw an InvalidPlan naming the value and the kernel at the first that fails:

  1. Every value a kernel stores is a member of that kernel's group and of no other; every value a kernel or a result reads is an input, a constant, or stored by a kernel earlier in the order.
  2. With storage, simulating the order: no slot is given to a value while the value it holds has a reader yet to run, but where a pair the storage records allows it, and each donated, staged, overwritten and reused pair holds by the rule that allows it, tested again; each lifetime covers its value's kernel and every reader.
  3. A recurrence's group has every state of its cycle first among its members, each carried from a different value it computes, and stores the values of the cycle no other kernel stores; each member outside the cycle rides its steps along them or at their last, and each fold of it is a sum that rides them, through values nothing stores.
  4. Each member's term loads values stored apart, its own only in a recurrence's; each member has a place within the domain; a fold read as a Stat is a primary fold of the group complete in an earlier phase; and a fold a term recomputes is not a member of the group.

in_place(k) says whether kernel k's realization reads each element a set of its outputs needs before it writes any of them, as storage was told. prepare checks every plan it forms, and its storage, with verify = true, the default when the environment sets TEMPEST_VERIFY=true, as the tests do.

Folds

Tempest.Compiler.IR.Relative — Type
Relative(law, observe)

A fold relative to a statistic of its own elements, in one pass. An element is (y, g...), or a number y, which is (y, 1). The state is the statistic's state over the elements so far and one sum of g · φ(y - m) for each g, where m is the statistic and φ the law's function: for the Exponential law, exp(y - m) against the maximum; for the Square law, (y - m)^2 against the mean. Each sum is relative to the statistic of the elements it covers, and combining two states moves both to the statistic of their union by the law's rebase: exp turns a difference of maxima into a factor, and a sum of squares about a part's mean moves to the whole's by n (μ_part - μ)^2. So softmax and the variance are each one pass, with no statistic computed first. The result is observe(law, state).

logsumexp is the exponential fold of a number observed as m + log(sum) (LOGSUMEXP); the sums a softmax weighs, and the sums of squares about a mean, become relative folds by rewrite (see rewrite).

source
Tempest.Compiler.IR.Exponential — Type

exp(y - m) against the maximum m. A sum relative to one maximum moves to a larger one by the factor exp(m_old - m_new). Exponentials are shifted by zero when the maximum is infinite, so an empty or all -Inf slice sums to zero, and a +Inf element to +Inf.

source
Tempest.Compiler.IR.Square — Type

(y - m)^2 against the mean m, whose state is the count and the sum. A sum of squares about a part's mean moves to the mean of the whole by n_part (μ_part - μ)^2 (Welford's algorithm, as Chan combines it).

Tempest.Compiler.Implement.GroupView — Type
GroupView

A group of the plan as implementations see it. A group computes its members over one domain: reductions, its folds, and outputs, its other values, each defined by its term in terms; a fold may cover fewer of the domain's positions (see own_domain). A :recurrence group's outputs are a recurrence's state, its term where the state starts; the values of its cycle it stores, in order; and last the value the state is carried from, the state one step on, stored only where something else reads it. Made once per executable, and once per decider for the claims it builds to time, when the first launch is built; nothing by default.

Libraries

A library realizes the groups that compute a function Tempest can already compute. It names that function as a template, and Tempest finds the groups that compute it and hands the library each array as a strided view.

Tempest.Compiler.Implement.Library — Type

A library realizes the groups that compute one of its templates on a target: Tempest matches them and hands supports and build a Binding of the template's arrays. claims, estimate, build_claim, record_name and candidates are Tempest's for a library.

Tempest.Compiler.Implement.Template — Type
Template(f; inputs, outputs)

A function a library computes, f, of arrays named and with named axes in inputs, as (A = (:m, :k), B = (:k, :n)), returning the arrays named in outputs, one name for each, in order. Tempest traces f with arrays of the axes' extents; an axis no axis of a group matches has extent one. An axis stands for the group's axes that the same arrays read, the same folds sum and the same index formulas (a causal mask's) move with. Axes alike in all three are interchangeable, as attention's query positions and the query heads that share a key head are: the library is offered a binding for each way, those whose arrays are laid out as inputs names their axes first.
