Tempest — Module

Tempest compiles traced Julia array programs into planned, fused kernels. See DESIGN.md for the design this code implements.

source

Compiling a function

Tempest.compile — Function
compile(f, args...; target, measure = true, capture = true) -> Compiled

f traced on args and prepared, to be called like f: compile(f, x)(y) computes f(y) for any y alike x in structure, shapes and element types. It returns what f returns, in arrays of its own, with numbers as numbers.

Which leaves of the arguments are inputs follows trace: arrays and numbers, also inside tuples, named tuples and immutable structs, except integers, which are constants. A call whose arguments differ in anything but the values of inputs throws, naming the difference.

julia> c = compile(x -> sum(abs2, x), [0.0, 0.0, 0.0, 0.0]);

julia> c([1.0, 2.0, 3.0, 4.0])
30.0

With capture, the program's launches are captured once as one graph that each call replays, as capture! does, unless the program has work on the host. Results are the same either way.

For a step that updates its state where it is and replays without copies, use prepare, bind! and execute!; c.executable is the prepared program, and explain(c) shows it.

Tempest.gradient — Function
Tempest.gradient(f, args...) -> (value, gradients...)

The value of f(args...), a number, and its gradient with respect to each argument, in that argument's structure: an array or a number for each floating-point array or number, and nothing for anything else. A struct's gradient is a named tuple of its fields'. On Julia arrays this is interpret(differentiate(trace(f, args...)), args...).

In traced code it differentiates f where it is called, so a training step is a function like any other, traced and prepared as one program:

function step(params, state, batch)
    loss, grads = Tempest.gradient(p -> loss_of(p, batch), params)
    new_params, new_state = adam(params, state, grads)
    (loss, new_params, new_state)
end

What f closes over is a constant to the gradient.

Tempest.explain — Function
explain([io], c::Compiled)
explain([io], ex::Executable)
explain([io], plan)

Print what Tempest decided for a program. For each kernel: what it computes, what it reads, and which values it stores or leaves to be recomputed where they are read. For a prepared program, also the precision of its products, the close calls measured between implementations, how values share storage, and which implementation runs each kernel, at what estimated or measured time.

It describes how Tempest keeps its promises today; what it prints may change.

Programs

Tempest.trace — Function
trace(f, args...) -> Program

Run f on stand-ins for args and record what it computes. Arrays and numbers among args, also inside tuples, named tuples and immutable structs, become the program's inputs, except integers: they are constants, so that they can be sizes, and an integer that varies between executions is an array of one. The results are arrays and numbers in the same kinds of structure, and nothing stays nothing.

julia> p = trace(x -> sum(abs2, x), [1.0, 2.0, 3.0])
Program with 3 nodes: Float64(3,) → Float64
  %1 = argument :: Float64(3,)
  %2 = map abs2 %1 :: Float64(3,)
  %3 = reduce sum over (1,) %2 :: Float64  [result]

Tempest.differentiate — Function
differentiate(program) -> Program

The program extended by its reverse pass. program must have one scalar result, the loss. The new program returns the loss and, in the structure of the inputs, the gradient with respect to every floating-point input (nothing for other inputs), with each struct a named tuple of its fields'.

julia> p = differentiate(trace(x -> sum(abs2, x), [1.0, 2.0, 3.0]));

julia> interpret(p, [1.0, 2.0, 3.0])
(14.0, [2.0, 4.0, 6.0])

Tempest.interpret — Function
interpret(program, args...) -> results

Evaluate program on Julia arrays and numbers, in the structure of its results, node by node: the reference that prepared programs are tested against, with no plan and no kernels.

julia> interpret(trace(sum, [1.0, 2.0]), [3.0, 4.0])
7.0

Tempest.@operation — Macro
@operation f(x::AbstractArray, w::AbstractArray; eps = 1.0f-6)

Make f an operation: on traced arrays it records a call of f rather than running its body, so the program keeps its name, an implementation can claim it and explain shows it. Each positional argument is an array of the type given (AbstractArray by default); keywords are passed on as written and are part of the call. Julia arrays among the arguments become constants. Eager execution is unchanged: Julia arrays still reach f's own methods.

The reference, the call's meaning in primitives, is f's method for the declared argument types run on traced arrays, unless Tempest.reference has a method for f. An operation whose body does not trace either gives a reference, or declares its results with Tempest.declared_results and is opaque.

rmsnorm(x, w; eps = 1.0f-6) = x ./ sqrt.(sum(abs2, x; dims = 1) ./ size(x, 1) .+ eps) .* w
@operation rmsnorm(x, w; eps = 1.0f-6)

Traced, rmsnorm(x, w) is one call in the program, which explain names; an implementation package may claim it with a kernel of its own, and where none does, it runs as the body above.

Prepared programs

Tempest.prepare — Function
prepare(program, inputs...; target, measure = true, replaces = (), by_reference = ()) -> Executable

Plan program for the shapes and types of inputs and build its kernels on target, chosen from the inputs' array types by default. Close calls between claims are timed when measure allows and the target can, and kept in the tuning record.

replaces declares state, as pairs result => argument of positions among the program's results and its arguments, alike in structure, shapes and types: (2 => 1, 3 => 2) for a step (params, state, batch) -> (loss, params, state). After each execution the argument holds the result, as if bound again, so the next execution reads it where it is. A result is written into the argument's storage when the kernel that writes it reads the argument only at the address it writes, and the kernels that read the argument otherwise can run first; else it is written apart and copied there after the last kernel. explain says which.

Inputs are copied into storage the executable owns, except the arrays at the positions in by_reference, which must be of the target's array type: they are the executable's storage. The caller keeps them alive and may write them between executions, and a result that replaces one writes into it.

A training loop, where the step returns the loss and the new parameters and optimizer state:

ex = prepare(trace(step, params, state, batch), params, state, batch; replaces = (2 => 1, 3 => 2))
capture!(ex)
for batch in batches
    bind!(ex, 3 => batch)       # only the batch is new
    loss, _, _ = execute!(ex)   # parameters and state are updated where they are
end

For a function called on new arguments each time, compile does the binding and copying.

Tempest.bind! — Function
bind!(ex, inputs...)
bind!(ex, position => input, ...)

Copy inputs into the executable's input buffers: all of them, in the structure prepare took them, or those at the positions given, as a new batch while parameters stay where the last execution left them. An array bound by reference and bound again is not copied.

julia> ex = prepare(trace(x -> 2 .* x, [1.0, 2.0]), [1.0, 2.0]);

julia> bind!(ex, [3.0, 4.0]);

julia> execute!(ex)
2-element Vector{Float64}:
 6.0
 8.0
source
Tempest.execute! — Function
execute!(ex) -> results

Run the program on the inputs bound last: replay its captured graph, or else run every kernel in order, then copy staged results into the arguments they replace. The results are outputs(ex), arrays over the executable's buffers that the next execution overwrites.

source
Tempest.capture! — Function
capture!(ex; repetitions = 1) -> ex

Capture the program's launches as one graph, which execute! replays from then on, each replay repetitions executions of the program (for timing). What varies between replays lives in device buffers: inputs bound by copy or by reference, scalars and seeds among them, are read where they are, so they need no new capture. Capturing again replaces the graph. A program with work on the host cannot be captured; on a target without graphs, replaying runs the kernels.

ex = capture!(prepare(p, CuArray(x)))
execute!(ex)                    # replays the graph
bind!(ex, CuArray(y))           # copied into the buffers the graph reads
execute!(ex)                    # the same graph, on the new values
source
Tempest.outputs — Function
outputs(ex) -> results

The results of the last execution, in the program's output structure, as arrays over the executable's buffers rather than copies: the next execution overwrites them, so copy what you keep. execute! returns them.
