API

Tempest — Module

Tempest compiles traced Julia array programs into planned, fused kernels.

A program is Julia array code, and what it computes reaches the compiler as three things: maps, folds (a scan is a fold that keeps the axis it runs along, a scatter one that combines each element at a position it computes), and reads at index formulas. Products, reshapes, permutations, gathers and scatters are spellings of them, and so is every function a program calls. Tempest names only what Base cannot spell:

  • the way in: compile, explain, gradient and the targets;
  • the derivative of a scalar function, which its code does not carry: scalar_partials;
  • the laws of a fold's combine: GenericFold.

A fold is Base's mapreduce, its state a tuple if need be, and a scan Base's accumulate; a fold's derivative comes from its combine's, through scans. A function given to mapreduce is taken to associate and commute, as a reduction groups and interleaves its elements; one given to accumulate is combined in sequence, as Base combines it, from an init that need be no identity. A GenericFold, given to reduce or accumulate where the function goes, claims that it associates and commutes, and so a scan by it may group its elements, as a sum's may.

logsumexp is a fold, a spelling. The log-sum-exp written out with maximum differentiates as it does, and plans as it does where the target permits the rewrites of sums (see Compiler.rewrite); it is named still because where a target keeps the rounding as written, the spelling is two passes, the maximum and then the sum, and logsumexp one.

Any other function, a product by labelled axes or a batched product say, is a spelling and lives in its own package, as Einops's and NNlib's do; an extension gives it a method on traced arrays where its body does not trace.

Tempest.Compiler is how a program becomes kernels; its public names are what packages beside a program need: the step beneath compile, what an extension writes traced methods with, and what kernel packages and targets read and define. Compiler.IR is the vocabulary its levels share and implementations read, and Compiler.Implement the interface kernel packages implement.

Compiling a function

Tempest.Compiler.compile — Function
compile(f, args...; target, measure = :close, capture = true) -> Compiled

f traced on args and prepared, to be called like f: compile(f, x)(y) computes f(y) for any y alike x in structure, shapes and element types. It returns what f returns, in arrays of its own, with numbers as numbers.

measure says which claims are timed when preparing, as for prepare: :none none, :close the options whose estimates are close, :all every option; true and false mean :close and :none.

Which leaves of the arguments are inputs follows trace: arrays and numbers, also inside tuples, named tuples and immutable structs, except integers, which are constants. A call whose arguments differ in anything but the values of inputs throws, naming the difference.

julia> c = compile(x -> sum(abs2, x), [0.0, 0.0, 0.0, 0.0]);

julia> c([1.0, 2.0, 3.0, 4.0])
30.0

With capture, the program's launches are recorded once as one graph that each call replays, as capture! and replay! do. Results are the same either way.

For a step that updates its state where it is and replays without copies, use the level beneath, in Tempest.Compiler: prepare, bind!, and execute! or replay!. c.executable is the prepared program, and explain(c) shows it.

Tempest.Compiler.gradient — Function
Tempest.gradient(f, args...) -> (value, gradients...)

The value of f(args...), a number, and its gradient with respect to each argument, in that argument's structure: an array or a number for each floating-point array or number, and nothing for anything else. A struct's gradient is a named tuple of its fields'. On Julia arrays this is interpret(differentiate(trace(f, args...)), args...).

In traced code it differentiates f where it is called, so a training step is a function like any other, traced and prepared as one program:

function step(params, state, batch)
    loss, grads = Tempest.gradient(p -> loss_of(p, batch), params)
    new_params, new_state = adam(params, state, grads)
    (loss, new_params, new_state)
end

What f closes over is a constant to the gradient.

Tempest.Compiler.explain — Function
explain([io], c::Compiled)
explain([io], ex::Executable)
explain([io], plan)

Print what Tempest decided for a program. For each kernel: what it computes, what it reads, and which values it stores or leaves to be recomputed where they are read. For a prepared program, also the precision of its products, the close calls measured between implementations, how values share storage, and which implementation runs each kernel, at what estimated or measured time.

It describes what Tempest decided today; what it prints may change.

Run on the CPU, through the same generated floor code CUDA runs.

Tempest.Compiler.CUDATarget — Type
CUDATarget(packages...; precision = :full, online = true)

Run on an NVIDIA GPU; needs CUDACore loaded. packages names the packages whose implementations the target may use, as in CUDATarget(cuTile); by default it uses every implementation available when a program is prepared. The floor is always used. precision is the numerics policy for products: :full keeps Float32 products in Float32, :tf32 allows TF32 tensor cores for them, and :tf32x3 splits each Float32 factor into two TF32 parts and sums three tensor-core products (close to Float32 accuracy). Half-precision products always accumulate in Float32. online permits the online softmax (see rewrite): a sum weighted by a softmax accumulates in one pass with the softmax's maximum, rescaled as it grows, which changes rounding.

Writing programs

Programs are written with Base: broadcasts, folds (mapreduce with a tuple state among them), scans (accumulate, cumsum), products, indexing and ranges (a range broadcast against a traced array is the index itself, a formula rather than an array). Beyond Base, programs can call logsumexp, and claim with a GenericFold the laws of a combine, which Base cannot spell:

Tempest.Compiler.logsumexp — Function
Tempest.logsumexp(x; dims = :)

log.(sum(exp.(x); dims)), computed stably in one pass.

source
Tempest.Compiler.IR.GenericFold — Type
GenericFold(; init, combine, lift = tuple, observe = only, pullback = nothing)

A fold from functions, given to reduce or accumulate where the operator goes. lift maps an element to a state tuple, combine merges two, the earlier first, and observe maps the last state to the result; init is a state tuple or a function of the element type returning one. It claims what Base cannot spell: that combine associates and commutes, up to rounding, and init is its identity, so a reduction or a scan by it may group its elements in any order. A function given to accumulate is combined in sequence instead. pullback(x, y, g, axes), when given, is the derivative rule of a reduction by it.

julia> recurrence = Tempest.GenericFold(; init = E -> (1.0, 0.0), lift = identity,
           combine = ((a1, b1), (a2, b2)) -> (a2 * a1, a2 * b1 + b2), observe = last);

julia> accumulate(recurrence, [(0.5, 1.0), (0.5, 1.0), (0.5, 1.0)])
3-element Vector{Float64}:
 1.0
 1.5
 1.75

Any other function a program calls, a batched product say, is written in these and lives in its own package. Where its body does not trace, an extension gives it a method on traced arrays, as NNlibExt and EinopsExt do, with these:

Tempest.Compiler.TracedArray — Type

An array a program is written with: a stand-in that records what is done to it as nodes of its tape. It is memory, as a Julia array is: an array the traced code allocates can be written, and views, reshapes and transposes share the memory of the array they are made from. A package that adds functions programs call defines them on it, in Tempest's primitives.

source
Tempest.Compiler.Traced — Type

A number a program computes: a stand-in for a scalar result such as sum(x), and, inside a broadcast, for an element of an array, which the broadcast's function runs on, each primitive operation it performs recorded. A package whose scalar function does not trace, a ccall say, defines it on Traced in operations that do; scalar_partials rules receive it too.

source
Tempest.Compiler.contract — Function
contract(a, b, la, lb, lo)

The product of a and b summed over shared axes, as an einsum: la and lb label the axes of a and b, lo those of the result, and labels of both factors missing from the result are summed over. Every product is one: a * b of matrices is contract(a, b, (1, 2), (2, 3), (1, 3)), and so is each product of an Einops einsum.

julia> Tempest.Compiler.contract([1.0 2; 3 4], [5.0 6; 7 8], (1, 2), (2, 3), (1, 3))
2×2 Matrix{Float64}:
 19.0  22.0
 43.0  50.0

Derivative rules

Tempest.Compiler.scalar_partials — Function
scalar_partials(f, g, y, xs...) -> tuple

The contributions of g, the cotangent of y = f(xs...), to each argument: one handle per argument, or nothing where the argument has no derivative. Arguments are elementwise handles; broadcasting is undone by the caller. Define a method for a function Tempest records whole (one that branches on its argument, say) to make it differentiable.

Tempest.Compiler

Tempest.Compiler — Module

How a program becomes kernels: the program, index and plan levels, the cover, code generation, the kernel cache, and prepared programs. Its public names are what packages outside it need: beneath compile, a program traced (trace) and prepared (prepare, bind!, execute!, capture!, replay! and outputs), for a step run in place; the language programs are written in, which Tempest makes its own, and what an extension writes traced methods with (TracedArray, Traced, contract); what implementations read of a plan beyond IR, and what they build kernels with (the kernel cache, generated and concurrently); and the protocol a package that adds a target defines (see Target).

Its submodules are IR, the vocabulary its levels share and implementations read, and Implement, the interface kernel packages implement. Their public names are what kernel packages read; the compiler also uses what they keep to themselves, such as the arithmetic that builds index expressions.

source
Tempest.Compiler.trace — Function
trace(f, args...) -> Program

Run f on stand-ins for args and record what it computes. Arrays and numbers among args, also inside tuples, named tuples and immutable structs, become the program's inputs, except integers: they are constants, so that they can be sizes, and an integer that varies between executions is an array of one. The results are arrays and numbers in the same kinds of structure, and nothing stays nothing.

julia> p = trace(x -> sum(abs2, x), [1.0, 2.0, 3.0])
Program with 3 nodes: Float64(3,) → Float64
  %1 = argument :: Float64(3,)
  %2 = map abs2 %1 :: Float64(3,)
  %3 = reduce sum over (1,) %2 :: Float64  [result]
source
Tempest.Compiler.prepare — Function
prepare(program, inputs...; target, measure = :close, replaces = (), by_reference = (), recompute = (), build = true) -> Executable

Plan program for the shapes and types of inputs and build its kernels on target, chosen from the inputs' array types by default. Close calls between claims are timed when measure allows and the target can, and kept in the tuning record. measure = :none times no claim but still uses the times in the record; :close, the default, times the options whose estimates are within the close-call factor of the best; :all times every option of every group and both sides of every comparison. true and false mean :close and :none.

replaces declares state, as pairs result => argument of positions among the program's results and its arguments, alike in structure, shapes and types: (2 => 1, 3 => 2) for a step (params, state, batch) -> (loss, params, state). After each execution the argument holds the result, as if bound again, so the next execution reads it where it is. A result is written into the argument's storage when the kernel that writes it reads the argument only at the address it writes, and the kernels that read the argument otherwise can run first; else it is written apart and copied there after the last kernel. explain says which.

Inputs are copied into storage the executable owns, except the arrays at the positions in by_reference, which must be of the target's array type: they are the executable's storage. The caller keeps them alive and may write them between executions, and a result that replaces one writes into it.

recompute pins folds to be recomputed where they are read rather than stored, by their numbers among the values of the program's index graph, as explain prints them: what the cover would otherwise decide by cost (see Tempest.Compiler.recomputable_folds). partition decides which of the forward's maps the backward recomputes rather than reads, by a minimum cut of what saving them costs (see Tempest.Compiler.partition); false saves every map the backward reads, as a trial's comparison.

build = false plans and decides but builds and allocates nothing: the executable can be explained, not run, on a machine without the target's device. No claim is timed, and claims are priced on nominal rates.

A training loop, where the step returns the loss and the new parameters and optimizer state:

ex = prepare(trace(step, params, state, batch), params, state, batch; replaces = (2 => 1, 3 => 2))
capture!(ex)
loss = first(outputs(ex))       # where each step leaves the loss
for batch in batches
    bind!(ex, 3 => batch)       # only the batch is new
    replay!(ex)                 # parameters and state are updated where they are
    @show loss[]
end

For a function called on new arguments each time, compile does the binding and copying.

source
Tempest.Compiler.bind! — Function
bind!(ex, inputs...)
bind!(ex, position => input, ...)

Copy inputs into the executable's input buffers: all of them, in the structure prepare took them, or those at the positions given, as a new batch while parameters stay where the last execution left them. An array bound by reference and bound again is not copied.

julia> ex = prepare(trace(x -> 2 .* x, [1.0, 2.0]), [1.0, 2.0]);

julia> bind!(ex, [3.0, 4.0]);

julia> outputs(execute!(ex))
2-element Vector{Float64}:
 6.0
 8.0
source
Tempest.Compiler.execute! — Function
execute!(ex) -> ex

Run the program on the inputs bound last, launching every kernel in order, then copy staged results into the arguments they replace. The results are in outputs(ex). Whether or not the program is captured, this launches kernel by kernel; replay! runs the capture.

source
Tempest.Compiler.capture! — Function
capture!(ex; repetitions = 1) -> ex

Record what execute! launches as one graph, for replay! to run, each replay repetitions executions of the program (for timing). Recording runs nothing. What varies between replays lives in device buffers: inputs bound by copy or by reference, scalars and seeds among them, are read where they are, so they need no new capture. Capturing again replaces the graph. On a target without graphs, a replay launches the kernels.

ex = capture!(prepare(p, CuArray(x)))
replay!(ex)                     # runs the graph
bind!(ex, CuArray(y))           # copied into the buffers the graph reads
replay!(ex)                     # the same graph, on the new values
source
Tempest.Compiler.replay! — Function
replay!(ex) -> ex

Run what capture! recorded, on the inputs bound last: what execute! does, repetitions times over, as one launch of a graph on a target with graphs. The results are in outputs(ex).

source
Tempest.Compiler.outputs — Function
outputs(ex) -> results

Where the executable leaves its results, in the program's output structure: arrays over its buffers, the same arrays every time, which each execute! or replay! fills again. Copy what you keep. A number is an array of no dimensions here, since it lives in a buffer too; compile returns numbers.

Folds

Tempest.Compiler.IR.Relative — Type
Relative(law, observe)

A fold relative to a statistic of its own elements, in one pass. An element is (y, g...), or a number y, which is (y, 1). The state is the statistic's state over the elements so far and one sum of g · φ(y - m) for each g, where m is the statistic and φ the law's function: for the Exponential law, exp(y - m) against the maximum; for the Square law, (y - m)^2 against the mean. Each sum is relative to the statistic of the elements it covers, and combining two states moves both to the statistic of their union by the law's rebase: exp turns a difference of maxima into a factor, and a sum of squares about a part's mean moves to the whole's by n (μ_part - μ)^2. So softmax and the variance are each one pass, with no statistic computed first. The result is observe(law, state).

logsumexp is the exponential fold of a number observed as m + log(sum) (LOGSUMEXP); the sums a softmax weighs, and the sums of squares about a mean, become relative folds by rewrite (see rewrite).

source
Tempest.Compiler.IR.Exponential — Type

exp(y - m) against the maximum m. A sum relative to one maximum moves to a larger one by the factor exp(m_old - m_new). Exponentials are shifted by zero when the maximum is infinite, so an empty or all -Inf slice sums to zero, and a +Inf element to +Inf.

source
Tempest.Compiler.IR.Square — Type

(y - m)^2 against the mean m, whose state is the count and the sum. A sum of squares about a part's mean moves to the mean of the whole by n_part (μ_part - μ)^2 (Welford's algorithm, as Chan combines it).

source
Tempest.Compiler.IR.Statistic — Type

The statistic itself: the maximum, or the mean.

source
Tempest.Compiler.IR.Sum — Type

The ith sum.

source
Tempest.Compiler.IR.Composed — Type

f of other observes and numbers: Composed(/, (Sum(1), Sum(2))) is the quotient of two sums. Called with a state alone, it composes the observes of a GenericFold, functions of the state.

source
Tempest.Compiler.IR.LOGSUMEXP — Constant

The log-sum-exp: the maximum plus the log of the sum of exponentials relative to it.

Tempest.Compiler.Implement

Tempest.Compiler.Implement — Module

The interface kernel packages implement. An implementation realizes groups of a plan as kernels: it claims the groups it can realize, estimates the launches of each claim, and builds them. It may also propose groups of its own. A package makes its implementations available with register! when it loads, and a target decides which of them it uses. Claims read a GroupView of the group, in the vocabulary of Tempest.Compiler.IR.

An implementation realizes groups of a plan as kernels. claims returns the ways it can realize a group, estimate the launches of each, and build_claim builds them. A target's floor realizes any group, so a plan never depends on an implementation.

Tempest.Compiler.Implement.GroupView — Type
GroupView

A group of the plan as implementations see it. A group computes its members over one domain: reductions, its folds, and outputs, its other values, each defined by its term in terms. A :scan group's reductions are scans along its primary_axes in one direction, which its members read at the position its sweep has reached. Folds over primary_axes, the axes its first fold not by key reduces, can be read within the group, and phase counts the folds each member waits for. values describes every value the group computes or reads, placement where it keeps each member (its index over the domain, or nothing), and bytes what it reads from storage and writes. reference(target, buffers) builds the group's reference kernels, the floor's, which every claim agrees with.

source
Tempest.Compiler.Implement.ValueView — Type

What a view holds of a value: its element type and dims, whether it is a number rather than an array (stored as one element), and whether it is stored; for a fold, the fold and the axes of its domain it reduces, and whether it is a fold by key (keyed), which reduces every axis and combines each element at its placement, after into where it is given: the contents it starts from, a term over its own domain; for a scan its fold, no axes, and scan: whether it runs from the last element down (reverse) and leaves each element out of its own prefix (exclusive), nothing for any other value; and for a value masked by formulas over its positions, masked: the formulas, each at most zero where the mask holds, and the number the value is where it fails (see Tempest.Compiler.IR.comparison_mask and Tempest.Compiler.IR.masked_result).

Tempest.Compiler.Implement.product_axes — Function
product_axes(group) -> (M, N, K, B) or nothing

The axes of a group whose folds each sum a product of two factors over the group's primary axes K: those only the first factor reads (M), those only the second reads (N), and those both read and keep (B). Nothing when a fold is not such a product, or the folds split the axes differently.

Tempest.Compiler.Implement.variants — Function
variants(implementation, target, group, claim) -> claims

The claims that vary claim, offered once it has measured best among the claims tried on group so far: the next stage of a search the implementation stages, as the generator stages its product tiles (every output tile at one depth, then the depths of the best and its split). The cover tries them in turn until the best has none new. None by default: then claims is the whole search.

source
Tempest.Compiler.Implement.Work — Type

One launch's work: bytes moved, flops of products whose factors are of type factor, flops of folds it recomputes inside them, its blocks, whether they split the sums among them, and the scalar functions it applies elementwise, each with the number of positions it is applied at. Tempest prices the bytes on its package's memory, the flops on the line its package reaches for products of that class, and each function on the time it measured for it on the device (see seconds). Functions applied inside a product's sweep, to its factors, are swept: each step's small tile of them stalls the sweep, and they cost many times what they cost streamed; those applied inside a fold the sweep recomputes, to that fold's tiles, are inner, at a factor of their own.
